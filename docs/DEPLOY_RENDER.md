# Deploying to Render (staging, Frankfurt)

Staging only. Use **synthetic data** (the "Demo Telecom" organisation). Real HR data is not allowed until IT/Legal data-residency sign-off is recorded (Plan D12).
Production is a second copy of these steps, done at the Leadership pilot gate, not now.

You need: a Render account with a paid plan (background worker, pre-deploy migrations and point-in-time recovery need it, OQ-B1-39), the repository pushed to GitHub, and `psql` on your computer.

## 1. Create the database
1. Render dashboard → **New → PostgreSQL**. Name `mentors-hub-staging-db`, region **Frankfurt (EU Central)**, PostgreSQL **16**, paid plan.
2. Under **Access control**, allow your own IP for the moment you run step 2 (remove it afterwards).
3. Copy the **External Database URL** (this is the admin connection; keep it out of the repository).

## 2. Create the two database roles (once)
Generate two long random passwords (e.g. a password manager) and run, replacing the placeholders:

```bash
psql "<EXTERNAL_DATABASE_URL>" \
  -v owner_pw="'<OWNER_PASSWORD>'" -v app_pw="'<APP_PASSWORD>'" <<'SQL'
CREATE ROLE mh_owner LOGIN PASSWORD :owner_pw NOSUPERUSER NOBYPASSRLS;
CREATE ROLE mh_app   LOGIN PASSWORD :app_pw   NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE;
SELECT current_database() AS db \gset
ALTER DATABASE :"db" OWNER TO mh_owner;
SQL
psql "<EXTERNAL_DATABASE_URL>" -c "ALTER SCHEMA public OWNER TO mh_owner;"
```

- `mh_owner` runs migrations only. `mh_app` is what the website and worker use; it must **not** own tables, be superuser or have BYPASSRLS (the test suite checks this).
- If `CREATE ROLE` is refused, the Render admin user lacks `CREATEROLE`: ask Render support to create the roles, or tell me and I'll adapt the setup.
- Never reuse the development passwords from `db/bootstrap.sql`.

## 3. Create the services from the blueprint
1. Render → **New → Blueprint**, pick the `mentors_hub` repository and the branch you pushed. It reads `render.yaml` and proposes `mentors-hub-web` and `mentors-hub-worker` (both Frankfurt).
2. When prompted for secrets, enter these. Use the database's **Internal** host (shown as the Internal Database URL) with the new roles, and add `?sslmode=require` only if you use the External host:

| Variable | Value |
|---|---|
| `DATABASE_URL` | `postgres://mh_app:<APP_PASSWORD>@<internal-host>:5432/<db-name>` |
| `MIGRATION_DATABASE_URL` | `postgres://mh_owner:<OWNER_PASSWORD>@<internal-host>:5432/<db-name>` |
| `APP_BASE_URL` | the service URL Render shows, e.g. `https://mentors-hub-web.onrender.com` (update when a custom domain exists) |
| `MAIL_FROM` | `Mentorship Hub <no-reply@your-sending-domain>` |
| `SMTP_URL` | any valid SMTP URL. Real email is blocked until IT sets up the sending subdomain with SPF/DKIM/DMARC; S0 sends no email. |

`SESSION_SECRET` is generated by Render. Set the same `DATABASE_URL`/`MIGRATION_DATABASE_URL` values on the worker service too (the blueprint shares the variable list, but each secret is entered per service).

## 4. First deploy and checks
The web service runs `npm run db:migrate` before going live; **a failing migration stops the release and the old version keeps running**.

1. Web service logs: expect `applied 0001 … 0012` and `migrations up to date`.
2. `curl -i https://<your-service>/api/health` → `200` and `{"status":"ok","checks":{"database":"healthy"}}`; the response carries `X-Frame-Options`, `Content-Security-Policy`, `Strict-Transport-Security`.
3. Worker logs show it started with no errors.
4. Remove your IP from the database access list.

## 5. Create the demo organisation and first admin (once)
Sign-in needs an organisation whose email domain matches your address. Run the demo seed from your computer against the **owner** connection (External URL, your IP allowed for this step):

```bash
git clone <your repo> && cd mentors_hub && npm ci
MIGRATION_DATABASE_URL="postgres://mh_owner:<OWNER_PASSWORD>@<external-host>:5432/<db>?sslmode=require" \
DATABASE_URL="postgres://mh_app:<APP_PASSWORD>@<external-host>:5432/<db>?sslmode=require" \
npm run seed:demo
```

This creates "Demo Telecom" with 8 synthetic people (domain `demo-telecom.example`, admin `admin@demo-telecom.example`). To sign in with a real mailbox instead, edit the domain/email in `scripts/seed-demo.ts` first. Real email needs a working `SMTP_URL`; until then the sign-in link is not delivered (the worker log shows the job failing, nothing leaks).

## 6. First sign-in check
1. Open `https://<your-service>/signin`, enter the admin email, receive the link/code, sign in on the **same browser**.
2. Accept the privacy notice, then enrol the authenticator app (TOTP) when prompted: admins must.
3. Open `/admin/roles` and `/settings`.

## 7. What this version contains / does not contain
- Contains: sign-in (magic link + code), sessions, TOTP for admins, consent, roles, EN/AZ/RU shell, tenant isolation (forced RLS), audit, worker, health.
- Not yet: programmes, people import, matching, sessions, reports, admin panel (later slices); Entra ID/Graph (L1/L2); real email; production environment; custom domain.
- Azerbaijani/Russian texts are provisional until native review (OQ-B1-38).

## Troubleshooting
| Symptom | Likely cause |
|---|---|
| `[ENV-001] invalid environment: …` | a variable is missing or malformed; the message names the variable, never the value |
| `[MIG-001] migration … failed` | the owner role lacks rights; check step 2 (`ALTER DATABASE/SCHEMA … OWNER TO mh_owner`) |
| `permission denied for schema public` | schema owner not changed to `mh_owner` |
| health returns `503 degraded` | `DATABASE_URL` wrong host, or `mh_app` password mismatch |
| worker: `permission denied … graphile_worker` | migrations did not finish; redeploy the web service so the pre-deploy step reruns |
